RESEARCH & PROPOSAL 01 / INFERENCE SYSTEMS

Faster is a number.
Better needs evidence.

A practical standard for measuring what quantization and inference optimization preserve—and what they quietly change—on a single DGX Spark.

TL;DR
  1. Qualify quality first; rank passing recipes by goodput.
  2. Goodput means correct, valid responses meeting latency limits per second.
  3. Compare against a frozen original-precision reference, SSD-offloaded if necessary.
  4. Test the model, context, batch composition, and load you intend to serve.
  5. Inconclusive ≠ pass. Report uncertainty and the time required to obtain it.

Scope: text LLM inference on one machine.

An inference stack can produce more tokens per second while becoming a worse system. It may lose useful answers, break structured output, truncate long prompts, or fail only when requests share a batch. A throughput chart does not tell us which of these happened.

For optimization work, the central question is comparative: does this specific change preserve the behavior we need from this specific model? For deployment, there is a second question: is the preserved behavior good enough for the application? Matching a weak reference answers only the first.

This article proposes Speed with Substance (SWS): a reproducible, quality-gated evaluation protocol designed for a single DGX Spark. The unit under test is an inference recipe. A recipe is the supplied model artifacts, software, and execution settings used to serve a model: checkpoint and tokenizer, deployed weights and precision, inference engine and version, kernels, cache policy, launch settings, and decoding policy. We test the supplied recipe as delivered; how it was derived is outside this evaluation’s scope. The engine is one component. We evaluate the complete recipe under a fixed workload and hardware profile; its quality and performance claims apply to that tested combination. The proposal synthesizes existing evaluation practice; its budgets and acceptance rules are recommendations to validate, not an established industry standard.

01 / ESTABLISHED PRACTICE

1. The closest gold standard

The closest established precedent for system benchmarking is MLPerf Inference: performance is evaluated against explicit quality requirements for a specified model, dataset, and scenario. Its rules include reference-relative targets, often 99% or 99.9% for particular benchmarks, and some LLM workloads also constrain output length. Those percentages are benchmark-specific, not a universal definition of acceptable quantization. A score of 80% retaining 99% of its value becomes 79.2%—a loss of 0.8 percentage points. [1]

Our inference: borrow MLPerf’s ordering—qualify quality before comparing performance—but add evidence for testing supplied quantized and optimized inference recipes. This protocol is not an MLPerf submission or certification.

What existing practice contributes
PracticeWhat to retainWhat it cannot establish alone

Executable and rule-based evaluationsVerifiable code and instruction outcomesAll open-ended writing, dialogue, or safety properties

The evaluation harness makes task execution and response logging reproducible, provided its revision, task configuration, and model interface are pinned. It is infrastructure, not a universal quality score. IFEval and EvalPlus supply complementary checks for instruction compliance and executable code correctness. [2] [3] [4]

1.1 Equal accuracy can hide different failures.

Accuracy is Not All You Need documents answer flips under compression: aggregate scores can remain similar while individual outcomes change. It motivates measuring both divergence and flips. Broader quantization studies also examine knowledge, alignment, and efficiency rather than perplexity alone, and find effects that vary by task and model. [5] [6] [7]

That is the measurement gap SWS addresses. It does not assume every changed answer is bad, or every unchanged answer is good. A harmful flip is an item answered correctly by the reference and incorrectly by the candidate. It records gains, losses, and changes separately.

02 / HARDWARE SCOPE

2. The one-Spark scope

This proposal covers workloads whose optimized inference stack can run on one DGX Spark, and quality tests that can complete in a reasonable time on that machine. We are interested in models that can run on a single DGX Spark, from 7B–14B models through 27B–120B+ dense and MoE models, including FP8 and FP4 recipes where memory permits. Fit must be measured; total parameters, active parameters, and nominal bit width alone do not establish it.

We believe these principles and methods also apply to multiple DGX Sparks and other machine configurations. We do not explore those configurations here. The working hardware profile is one 128 GB GB10 Spark; 273 GB/s is NVIDIA’s specified memory bandwidth, not a measurement in this article. CPU and GPU share memory. [8]

2.1 Budget the candidate and the evaluation separately

MEMORY BUDGETpeak memory ≈ weights + KV/recurrent state + workspaces + runtime + OS

At two bytes per parameter, 120B original-precision weights require roughly 240 GB before overhead. Their failure to fit RAM does not disqualify an on-Spark quantized candidate. For conventional attention, estimate KV storage as 2 × layers × KV heads × head dimension × cached tokens × bytes per element, summed across sequences; measure actual allocations, including quantization metadata and architecture-specific state, without double-counting unified memory.

2.2 Generate the original-precision baseline from SSD

Use a trusted implementation that keeps original checkpoint weights on SSD and stages the required modules into bounded CPU/GPU memory on demand. Hugging Face Accelerate supports checkpoint dispatch with disk offload. The accompanying reference utility uses that mechanism and explicit memory budgets; it has not yet been validated on the target Spark. Validate each architecture and compare a small model or shard against a resident reference before trusting a new offload path. SSD loading changes placement; it must not silently quantize weights or alter the model. [16]

Run the frozen original-precision evaluation once, save its per-item outputs and scores, and reuse them across candidate recipes. Archive the exact prompt tokens, generated tokens, generation settings, model revision, and scoring metadata. Save teacher-forced full-vocabulary log probabilities on identical, fixed prefixes in bounded shards when distribution comparison is required. Chosen-token log probabilities alone do not support full-vocabulary KL. Reference repeats on a small subset still establish numerical and sampling variability.

The SSD-backed reference is a quality baseline; its throughput is not the candidate’s performance baseline. Keep quality-reference time and candidate serving time separate. Disk traffic can dominate: profile a short shard, estimate full-suite time from measured seconds per prompt/token, and record SSD read volume and reload overhead. Prefer amortizing loads across fixed teacher-forced sequences where memory permits; autoregressive decoding may reload modules for every token.

2.3 Set an explicit wall-clock budget

Before running, record an affordable budget for screening, reference generation, and final confirmation. For example, an operator might allocate one hour for screening and an overnight window for reference generation; these are planning choices, not promised runtimes. Cache immutable reference artifacts so this cost is paid once per protocol revision. If a required confidence bound cannot be established within the budget, narrow the claim or report inconclusive.

If an original-precision run is unavailable or unaffordable, report preservation as unmeasured; the recipe cannot qualify for an original-precision preservation claim. Obtain the reference artifacts before making that claim. Comparing a larger quantized model with a smaller resident model answers a deployment-choice question, not quantization loss.

03 / EXPERIMENTAL CONTROL

3. Define the test record

3.1 Record the reference

Use the original released checkpoint in its native high precision, typically BF16 or FP16, through a trusted implementation as the reference. BF16 is an engineering baseline, not mathematical ground truth. If the model was released only in a quantized format, name that limitation; do not call a dequantized copy an original BF16 reference.

Before testing an optimization, repeat the reference and establish its own variability across process restarts and batch shapes. Greedy decoding reduces sampling variance, but floating-point reductions and near-tied logits can still change tokens. Do not require bitwise identity across unrelated kernels as a universal acceptance criterion.

3.2 Record the recipe

A recipe is the supplied combination of model artifacts, software, and settings that we run and evaluate. We need enough information to execute that same recipe again. We do not need to reconstruct how its author selected, trained, calibrated, or optimized it. The engine is one ingredient; the execution record includes the following.

What constitutes an inference recipe
IngredientWhat to record
Source modelCheckpoint revision and weight hashes; tokenizer, chat template, and special tokens.
Deployed model artifactsExact weight files and hashes, format and precision, and configuration files needed to load them. Record the supplied artifacts as tested; quantizer history and calibration data are not required.
Engine and buildEngine/runtime version or container digest, installation or build commands needed to run the supplied software, compilation options, kernels, and relevant dependencies.
Serving settingsLaunch command, weight/activation/KV precision, cache policy, scheduling and batching limits, chunked prefill, and speculative decoding settings.
Generation policyContext and output limits, truncation, reasoning mode and budget, stop handling, temperature, top-p/top-k, penalties, and seed policy.

Store this execution record in a versioned manifest with an immutable recipe ID. Another operator should be able to obtain the same supplied artifacts and software and launch them with the same settings. “Engine X with FP4” is insufficient because it does not identify the actual weights or execution settings. If the supplied artifacts, software, or settings change, record and test the new recipe revision.

Compare the deployed recipe with the original-precision reference. Use the same evaluation inputs, prompt formatting, scoring rules, and generation policy for both, except for an explicitly declared recipe change under test. The reference may use another trusted implementation and SSD offload; the candidate engine need not support its precision. Record hardware, workload, and evaluator versions alongside the recipe so readers know where the result applies. A different prompt or scoring protocol is a different evaluation, not evidence of a recipe improvement.

Report the candidate-minus-reference difference as the complete recipe’s effect. That comparison measures overall preservation; it does not isolate which ingredient caused a change. The release decision applies to the final recipe, including interactions between quantization, kernels, caches, compilation, and decoding.

3.3 Record the environment

The environment is the machine and system software on which the recipe is tested. Record the NVIDIA driver version explicitly for every run; “DGX Spark” or a container tag alone does not identify it. Also record the Spark model and installed memory, OS/kernel, CUDA runtime and relevant libraries, container digest, and power/clock settings. The host driver remains part of the environment even when the engine runs inside a container.

Give the environment record a versioned ID. A driver update creates a new environment revision, even if the recipe and benchmark are unchanged. Record reference and candidate environments separately if they differ. For reproduction, preserve the tested versions where practical; if a rerun uses a different driver or system configuration, identify that difference rather than silently treating the run as identical.

3.4 Record and publish the benchmark

The benchmark is the versioned test contract: tasks and dataset revisions; splits and item IDs; prompt rendering; generation settings and token budgets; load schedule and concurrency; scoring and answer extraction; quality margins and confidence method; and latency limits and timing boundaries. Give the entire suite an immutable version, including its harness, scorer, and configuration hashes. A dataset name alone is insufficient. A change to any of these rules creates a new benchmark version.

Every published result must include a runnable benchmark package. Provide the data or pinned download/generation instructions, the exact scripts and commands to run the reference and candidate, the scorer and analysis code, dependency versions, configuration, and raw per-item and timing artifacts. Where the reference is cached, provide its hashed artifacts and the command that generated them. Respect dataset redistribution terms by publishing acquisition instructions and checksums when the data cannot be bundled. Readers must be able to regenerate the quality decision and performance summary.

The benchmark package contract specifies the required files. The benchmark-run wrapper checks input hashes, runs a package’s pinned commands, and records logs, exit codes, runner identity, and driver information. It is execution plumbing, not a scorer or a completed benchmark suite; each result must supply its actual benchmark and analysis commands. No benchmark run has been performed yet.

A result is identified by reference version + recipe version + environment version + benchmark version. Freeze all four before measurement and link them from the results board. Reproduction checks should compare the quality decision and performance within stated uncertainty, rather than assume bitwise-identical outputs.

04 / THE PROPOSED PROTOCOL

4. Four layers of evidence

L1

4.1 Numerical fidelity

Did the probability distribution change?

Start below the logits: compare kernel and layer outputs using RMS, maximum absolute error, and relative error with a defined denominator floor. Include extreme values, noncontiguous layouts where supported, odd shapes, and relevant context/batch sizes. Locate the first divergent layer before interpreting end-to-end quality. Tail error is a diagnostic signal, not by itself proof of a user-visible failure.

Teacher-force identical held-out token sequences into both systems: each scored position must have exactly the same prefix. Compare at temperature 1 before sampling filters. Align vocabulary IDs, positions, masks, and normalization; full-vocabulary KL is invalid when tokenization differs. Include natural text, code, and application examples, plus response positions on frozen reference-generated trajectories. Analyze these strata separately.

  • Negative log-likelihood (NLL) and perplexity: report candidate minus reference NLL in nats/token and the perplexity ratio exp(ΔNLL). Fix context windows, stride, document boundaries, and scoring masks.
  • Forward KL: average Σᵥ p_ref(v|prefix) log[p_ref(v|prefix) / p_cand(v|prefix)]. Compute with stable log-softmax and adequate accumulation precision. Report mean and tail quantiles, not just a single average.
  • Top-1 disagreement and logit margin: separate flips near ties from changes where the reference’s leading token had a large margin. Neither is automatically a task failure.

KL is a fidelity diagnostic, not a certificate of correctness or safety. There is no universal “safe KL” cutoff across models and domains. An alert band is a preregistered diagnostic range whose violation triggers investigation. Set these ranges using reference repeatability and a separate evaluation pilot, and preregister them. A breach triggers investigation; it cannot replace the task gate.

If an endpoint exposes only generated text, run the other layers and mark full-distribution fidelity unmeasured. Top-k log probabilities with the tail discarded are not full-vocabulary KL. A shared top-k union plus an “other” bucket can give a coarsened comparison when exact tail masses are available; label it as such. An offline logits adapter diagnoses the model but does not prove the deployed server follows the same path.

RULER exercises more than a single needle lookup, but its authors explicitly caution that synthetic tasks cannot replace realistic ones. Compression safety research also shows why preserved language-model loss cannot establish preserved safety behavior. [4] [3] [9] [10]

4.3 A deeper profile for reasoning and coding models

The inexpensive suites above are a starting point. For a capable reasoning or coding model, add GPQA Diamond, a pinned LiveCodeBench release and problem-date window, and long-context reasoning. Use AIME and SciCode for deeper math and scientific-programming evaluation when those workloads matter. Include BFCL for tool-call behavior and a fixed-version τ²-bench domain for multi-turn agents when relevant. Avoid tests on which the reference is already near a floor or ceiling; difficulty alone does not make a test sensitive to quantization.

NVIDIA Model Optimizer’s guidance lists GPQA, SciCode, and LCR as a standard quantization-validation selection, while its default scope specifies a broader suite. These are useful project recommendations, not a universal standard or empirically guaranteed sensitivity ranking. Its LCR recipe targets roughly 120K input tokens: use it only when the checkpoint and one-Spark memory budget support it. A shorter RULER or document-QA test is a different evaluation, not an equivalent LCR score. [12]

Freeze benchmark versions, answer extraction, reasoning mode, generation budget, and pass@1 versus pass@k semantics. Repeated AIME generations estimate sampling variability on the same questions; they do not create new independent math problems. Analyze repeats within question clusters and distinguish a precise score on a fixed test from evidence about broader mathematical ability.

For each binary-scored family, publish the four paired counts: both correct, reference-only correct, candidate-only correct, and both wrong. Report net score change, harmful flips per all items, and lost-answer rate: reference-only correct divided by reference-correct items. If that denominator is zero, the rate is undefined. “Both wrong” is not evidence of output agreement; record semantic or answer agreement separately where meaningful.

Use greedy generation for an initial diagnostic pass. If production uses sampling, also test that distribution with repeated seeds and the actual decoding settings. Shared seeds do not guarantee matched random trajectories across engines. Treat repeated generations as clustered within a prompt. For open-ended answers, blind and randomize the presentation order, use an anchored rubric, and audit judge disagreements with humans. A local model judge can share the candidate’s weaknesses; do not make its preference the sole release gate.

L3

4.4 Context and serving correctness

Does quality survive the execution path?

Test the actual endpoint at supported context lengths—start at 4K, then 16K and 32K only if the model and memory budget permit—and client concurrency 1, 2, 4, 8, 16, and 32 where feasible. Use identical examples across configurations and stratify by context length. Long-context probes should vary evidence position and include retrieval, multi-hop reasoning, and distractors. An advertised window is a capacity limit, not a guarantee of useful recall.

4.5 “Results may vary with batch size” is a testable claim.

BATCHING POLICY

Results may depend on batching, but the dependence must be measured and bounded. A quality claim applies only to the tested batching regime. Numerical variation can be acceptable; functional errors cannot. Task-level variation must satisfy the same preregistered quality gates used for other optimizations.

Batching policy is part of the recipe; actual batch composition and size are part of its tested operating regime. Throughput and latency changes are expected. Kernel selection and floating-point reduction order can also change numerical results; a different generated token, particularly near a probability tie, does not by itself prove a defect. A task-quality regression still needs to meet the declared acceptance margin. Incorrect masking, request mix-ups, and cache contamination are correctness failures, regardless of average benchmark scores.

Client concurrency is not execution batch size. Concurrency counts outstanding requests. With continuous batching, the scheduler can combine different sets of active sequences at successive steps, and a token budget can constrain prefill work independently of sequence count. Record the maximum sequence and batched-token limits, scheduling and chunked-prefill policy, request arrival trace, and observed sequence/token batch sizes where instrumentation permits. If actual batches are unobserved, report that limitation rather than labeling a concurrency setting as a measured batch size.

  1. Replay the same prompts alone and together. For controlled batch tests, vary supported batch sizes, composition, request order, and sequence lengths. Hold prompt formatting and decoding settings fixed. Include representative mixed-length continuous-batching traffic, not only uniform synthetic batches.
  2. Measure the reference’s sensitivity. Repeat the reference across batching regimes and process restarts. Compare the candidate with the reference under matched regimes, then compare each system with its own single-request behavior. This helps separate inherited numerical variability from a new optimization effect; reference variability is not a waiver for application failures.
  3. Qualify every claimed regime. Apply the preregistered quality and correctness gates to each required batch or serving-load slice. A pass at batch size 1 does not qualify batch size 8. Define the tested range and traffic distribution in advance; a finite set of tests cannot guarantee every possible batch composition.

Stress mixed-length batches, left/right padding where supported, chunked prefill, prefix-cache hits and misses, KV-cache precision, repeated requests, cancellation, stop strings, and streaming assembly. Alternate distinct prompts with similar prefixes to detect cache contamination or response mix-ups. Compare the same request alone and in a batch. Speculative decoding needs task and distribution checks under its actual verifier and sampling implementation, even when the algorithm is intended to preserve the target distribution.

Count timeouts, out-of-memory errors, malformed responses, silent truncation, and invalid task outputs in the denominator. Do not score only completed requests. A quality pass at concurrency 1 does not qualify concurrency 4. An unsupported configuration is marked unsupported; an attempted run that fails remains a failure.

L4

4.6 Quality-qualified performance

How much useful work survives the latency budget?

Only recipes that clear the declared quality and correctness gates enter the qualified speed comparison. Report time to first token, inter-token latency or time per output token with an explicit definition, end-to-end latency, output tokens/second paired with ms/output-token, requests/second, and memory. For one serial decode stream, ms/token = 1000 ÷ decode tokens/s over the same interval. Aggregate throughput at concurrency is not per-user token latency: pair aggregate tok/s with measured per-stream ms/token (and its distribution), never its reciprocal. Show latency distributions, including p50 and p95, with sample counts. Small runs cannot support precise tail estimates.

PRIMARY DEPLOYMENT METRICgoodput = correct, valid responses meeting the SLO / measured wall-clock seconds

Define the service-level objective (SLO) before running: for example, a workload-specific first-token limit and completion deadline. A response counts in this numerator only if it satisfies all declared conditions. Use objectively scored tasks for this metric; for ungraded open-ended traffic, call it SLO-compliant throughput rather than correctness-qualified goodput. Also retain raw throughput so the source of any gain remains visible.

Use the same request trace, arrival policy, prompt lengths, and generation budgets. Report actual output lengths, stop reasons, and reasoning tokens where available; shortened or incomplete answers can inflate apparent speed. Separate cold startup, compilation, warm serving, and intentional cache reuse. For sequential runs, alternate reference/candidate order, allow comparable thermal conditions, and measure several independent runs. Record background processes, power mode, clocks, temperatures, and throttling. Measure energy only with a stated instrument and scope.

05 / ACCEPTANCE, NOT IMPRESSION

5. A defensible decision

Failure to detect a drop does not establish preservation. Use a paired non-inferiority test: decide in advance how much degradation is tolerable, then ask whether the uncertainty interval excludes a larger loss. Apply this per required task family and deployment slice; do not let improvements in one family compensate for a regression in another.

Let dᵢ = candidate_correctᵢ − reference_correctᵢ, so each paired observation is −1, 0, or +1. The mean Δ is the score difference. For a preregistered absolute margin δ, the quality gate passes only if a one-sided 95% lower confidence bound for Δ is above −δ. Report the point estimate and interval in percentage points.

PASS

Lower bound > −δ, retention gate and application floors met, and correctness gates clear.

FAIL

Upper bound < −δ, or a declared critical correctness gate fails.

INCONCLUSIVE

The interval crosses the boundary. Collect more evidence; do not qualify the speed claim.

For a three-way decision, compute both one-sided 95% bounds (equivalently, the endpoints of an equal-tailed 90% two-sided interval). Prefer a validated paired-binomial score or exact method for binary outcomes, especially with few discordant pairs. Tango’s paired-proportion score interval is one established option; validate boundary cases in the implementation. [11] A paired prompt-level bootstrap is useful for nonbinary metrics and adequately populated samples, but a naive bootstrap collapses when all pairs agree. It must not certify zero uncertainty in that case. Never treat correlated tokens, instructions within a prompt, or multiple samples of one question as independent observations.

A simple conservative fallback is to bound harmful flips alone. If r is the fraction of all items that change from correct to incorrect, then Δ ≥ −r. An exact one-sided binomial upper bound for r therefore supplies a conservative lower bound for Δ, ignoring beneficial flips. For zero harmful flips in n independent prompts, its 95% upper bound is 1 − 0.05^(1/n), approximately 3/n. With 300 items and no harmful flips, the bound is still about 1%; zero observed losses is not proof of zero risk.

5.1 Proposed starting gates

NVIDIA Model Optimizer’s recipe-search guidance also uses a default per-benchmark budget of one percentage point against a matching BF16/FP16 baseline. That is an engineering policy, not a statistical guarantee. [14] The following are illustrative policy choices, not thresholds validated for DGX Spark or endorsed by the cited benchmarks. Freeze them before testing, justify them against application needs, and report insufficient evidence honestly.

GateExample preregistered rule
Task preservationFor each required family and supported context/concurrency slice: lower confidence bound for Δ > −1 percentage point.
Behavioral retentionUpper confidence bound for lost-answer rate < 2%, with the reference-correct denominator reported.
Absolute usefulnessMeet a separately specified minimum application score, even if the reference is weak.
Critical serving behaviorZero observed response cross-contamination or silent truncation in the declared fixture suite. This is a finite-suite check, not a population guarantee.
Numerical diagnosticsPublish NLL, KL, disagreement, and reference repeatability; investigate preregistered alert-band violations before release.

When all preregistered family gates must pass to make one joint preservation claim, the intersection-union construction controls false acceptance at the individual test level under its assumptions. Separately advertising many individual passes, selecting among many candidates, or repeatedly checking accumulating results introduces different multiplicity issues. Use adjusted intervals, a fresh confirmatory set, or a preregistered sequential procedure as appropriate; do not repeatedly sample until a favorable interval appears.

Plan sample size from an evaluation pilot’s discordant-pair rate and a desired power, such as 80% or 90%, under an explicit expected effect. As a precision illustration only, if about 10% of independent pairs disagree and Δ is near zero, the standard error is approximately √(0.10/n). A one-sided 95% margin near one percentage point then needs roughly 2,700 items. That is not a powered sample-size calculation; adequate power can require substantially more. A 200-item smoke test should catch breakage, not substantiate a one-point preservation claim.

06 / ONE-SPARK RUNBOOK

6. A practical runbook

  1. Freeze the experiment. Pin the supplied recipe and reference artifacts, choose workload slices, and register margins, floors, exclusions, seeds, and planned sample sizes. Keep evaluation-pilot data separate from confirmatory data when the pilot informs the test design. Store the manifest before seeing final outcomes.
  2. Verify the reference. Confirm memory fit and prompt/token agreement. Repeat a representative subset across fresh processes. Generate and archive the original-precision reference artifacts, using SSD offload when needed. If the reference is unavailable, mark preservation unmeasured.
  3. Check the supplied recipe cheaply. A suggested screening budget is 200 task prompts, 32 serving fixtures, and 20,000–100,000 teacher-forced positions. Sample by document and domain. These are engineering budgets, not certification-sized samples.
  4. Inspect discrepancies. Record harmful flips, confidence margins, numerical tails, long-context losses, and format errors. Check the evaluation setup for mistakes; do not modify the supplied recipe to improve its score. If a new recipe revision is supplied, evaluate and identify it separately.
  5. Run the fixed quality evaluation. Prefer full official suites for published benchmark scores. Any subset must be fixed, identified, and labeled as a subset. Use pilot-based power planning for the application suite and repeat production sampling within prompt clusters.
  6. Benchmark qualified recipes. Replay the same workload, with quality probes under the actual serving load. A proposed starting point is five independent warm runs plus separately reported cold runs; extend the design if uncertainty is too large.
  7. Publish a qualified claim. Include failures, inconclusive gates, unsupported slices, raw paired evidence, and immutable recipe IDs and workload profiles. Re-run the relevant layers whenever the model, runtime, kernels, template, or cache policy changes.

Do not promise a universal “overnight” runtime. Profile a small evaluation-pilot shard and estimate number of requests × mean request time for serial execution, then add prefill, model reloads, repetitions, and evaluator overhead. Long-context and code-generation workloads may dominate. If the confirmatory suite exceeds the available budget, reduce the scope of the claim or report it as inconclusive; do not relax thresholds after seeing the result.

6.1 Separate the test machine from evaluation infrastructure.

“One DGX Spark” constrains the candidate inference system. It does not automatically mean the entire evaluation runs locally. Agentic and judge-scored recipes may require a user simulator, model judge, sandbox, or external API. Declare every dependency, keep judge and simulator versions fixed, and record their seeds, retries, token budgets, and cost. If strict all-local evaluation is required, schedule auxiliary models separately where feasible and report any changed evaluation protocol. Shared-memory contention from a judge must not contaminate the candidate’s performance run. NVIDIA’s recipes explicitly identify several judge and simulator dependencies. [12]

NeMo Evaluator’s nightly documentation offers paired flip analysis, statistical comparisons, and suite-level policy gates. It is a useful implementation option, but pin and inspect the exact release. An ordinary McNemar test detects unequal paired success rates; failure to reject equality does not establish non-inferiority within a chosen margin. Verify that the configured release gate implements the confidence-bound rule above rather than treating “no significant regression” as preservation. [15]

Use the evaluation harness for supported task adapters, official IFEval and EvalPlus scorers for their respective suites, and RULER’s generator with fixed seeds for synthetic context tests. Archive per-sample outputs, not just leaderboard summaries. ARM64 package support, model formats, logits access, and kernel availability must be checked for each chosen runtime on Spark; this article does not claim that every stack supports every proposed precision mode.

07 / THE PUBLIC RESULT

7. Publish the evidence

A recipe is qualified only over its tested model, domains, context lengths, decoding policy, concurrency, and latency budget. Call this its quality envelope. Outside that envelope, the result is unknown.

EXAMPLE CLAIM FORMAT · PLACEHOLDERS ONLY

“The candidate recipe passes all preregistered task-preservation and application gates against the original-precision reference at [context lengths] and [concurrency], using [decoding policy]. Its goodput is [value with uncertainty] under [SLO]. Numerical fidelity is [measured / limited / unmeasured]. Untested recipe revisions and operating regimes are excluded.”

A report should contain the following linked artifacts:

  • Reference and recipe records: immutable versions, supplied artifact hashes, original checkpoint and tokenizer identity, software installation/build and launch commands, precision choices, cache settings, and decoding policy. The record reproduces execution, not the recipe’s derivation.
  • Environment record: immutable version, actual NVIDIA driver version, Spark hardware and memory, OS/kernel, CUDA/runtime libraries, container digest, and power/clock settings.
  • Benchmark package: immutable suite version, data or pinned acquisition instructions, prompts and workload configuration, harness/scorer/analysis code and revisions, setup and rerun commands, confidence method, margins, absolute floors, and decision rules.
  • Per-item evidence: reference and candidate outputs or permitted hashes, scores, paired categories, token counts, stop reasons, and errors. Respect dataset licensing and redact private application data; publish reproducible fixture substitutes where needed.
  • Performance record: timestamped request traces, cold/warm policy, arrival schedule, client concurrency, scheduler limits and observed execution batch sizes where available, timing boundaries, memory and thermal telemetry, and run-level uncertainty.
  • Decision table: one row per recipe revision and required slice, with pass/fail/inconclusive/unmeasured status. Show raw speed for failures only as clearly unqualified results.

Plot quality-qualified goodput against memory or latency, retaining only points that pass the required gates. Show accuracy deltas and harmful-flip rates alongside the plot. If one candidate is faster but uses more memory, present the trade-off rather than hiding it inside a weighted “overall score.”

The optimization target is not the fastest stream of tokens. It is the most useful work this machine can deliver within a declared quality and latency budget.

On one DGX Spark, that is measurable—if the reference, the workload, the uncertainty, and the limits of the claim are part of the result.
